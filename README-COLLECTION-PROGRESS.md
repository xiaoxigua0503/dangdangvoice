# Collection reliability and report progress

This change targets the existing Node/PostgreSQL/VM Web and report-worker services. The third service, `dangdangvoice-chat-worker`, and DiDi's UI/queue/prompt/schema are untouched. No production crawling, inference, email, migration, restart or deployment is part of this source update.

## Confirmed source defects and limits of diagnosis

The previous relay marked missing product names, JSON parse failures and network/HTTP failures as `blocked`. The browser also treated `items=[] && total>0` as an inaccessible channel, so a valid summary containing total=79, auto=79, pageCount=0 could enter retry instead of finishing. The queue's `tries % 3` reset the backoff. These defects were confirmed in source; the supplied production product observations were not recrawled.

The old list parser used the first link or the entire `.describe_detail` text; detail used the entire `.describe_long` text. Nested login/action controls could therefore enter review text. The new parser reproduces and prevents that case with fixtures by removing structural form/button/login/action nodes inside the known content node, not deleting sentences containing 登录. A real review mentioning 登录 remains intact. No original HTML for the suspected historical contaminated report was available locally, so this is not a claim that its exact production cause was proven or its saved data repaired.

## Relay contract and collection correctness

[collection-parser.mjs](./server/collection-parser.mjs) contains the existing list/detail/product selectors and rating extraction, plus explicit outcome classification. It is shared by the relay and offline checks. Rating values and the existing star-width conversion are unchanged. Image-only review rows remain valid; comment photos are not discarded just because text is empty. Product metadata honors a declared UTF-8 charset while retaining the existing GB18030 fallback for legacy book pages. A detail parser failure never replaces valid list text.

Responses preserve `ok`, `blocked`, summary/items/fields/meta/cookies and add `outcome`, `stage`, `httpStatus`, `code`, optional `retryAfterMs` and bounded parser counts. Outcomes are `blocked`, `rate_limited`, `timeout`, `network_error`, `upstream_error`, `parse_error`, `unsupported_response`, `empty_confirmed`, `defaults_only`, `empty_unconfirmed`, `partial`, `completed` (plus `cancelled` for aborted transport). Default logs include action/product/status/code only, not cookies, full HTML or source text.

WAF classification requires an access-denied HTTP response or recognizable challenge script/title, not missing metadata or invalid JSON. Unknown JSON/schema/HTML is a parser/unsupported outcome. Parsed rows with incomplete summary or rejected sibling rows are retained as partial results. A zero-row response needs recognizable list schema and valid totals/page count. Empty markup alone is not evidence; a login/error screen cannot confirm zero. Valid zero total with zero/one page confirms no public comments. Valid total>0, auto=total, pageCount=0 with no public text confirms defaults-only. Other empty responses stay unconfirmed. pageCount=0 is never called a site depth limit.

Confirmed empty/defaults-only results keep actual metadata and site summary, create zero user-written rows, end without automatic retry and cannot create a review-AI job. `preview.noPublicComments` communicates that guard; the flag is a side channel and is not added to the report's model input. Existing saved runs/reports are not rewritten. Basic results still preserve site totals separately from actual collected comment counts.

Metadata, list and detail statuses are stored separately in the new snapshot's site information. Metadata failure cannot discard successful comments. A single later product-page attempt may recover missing metadata, except after access/failure limits are reached. Exact-product detail metadata remains required; grouped/variant detail pages cannot supply another product's identity. Only real product-page fields are retained (including price/cover where present), with product ID and requested URL as neutral fallbacks. Missing metadata is disclosed. New-row comments without a source cid remain with null cid and a local page key, with a cross-page deduplication warning; no original cid is invented.

## Queue, ownership, cancellation and limits

[collection.ts](./src/collection.ts), [api.ts](./src/api.ts) and the bounded browser loop in [App.tsx](./src/App.tsx) use monotonically increasing 20/40/80/120-second backoff, respecting a larger Retry-After. The schedule uses accumulated failures across retries rather than restarting after a cycle. There are at most 8 failed requests, 6 queued cycles and 15 minutes per automatic collection intent. Normal successful page/detail pacing remains. Two consecutive access denials pause further attempts; parser/unsupported/unconfirmed empty responses also pause for manual review. These are source constants, not new environment variables and not report retry-budget settings.

The existing v1 localStorage queue remains readable and deduplicated by owner/product. Paused/stopped entries cannot auto-run. Expired/exhausted legacy entries become paused on read; their accumulated retry state is retained. Stop retains a tombstone when a queue entry exists, so a late failure cannot revive it. A manual retry explicitly starts a new bounded intent, but an upstream Retry-After cooldown is persisted and must expire first, even after stop. No anonymous/other-owner queue entry starts automatically.

Migration [011_ai_display_phase.sql](./migrations/011_ai_display_phase.sql) adds a short PostgreSQL `collection_leases` table. The Web owns an exclusive owner/product token for each new run, renewed during the run/every 20 seconds, expiring after 60 seconds without renewal and bounded to a 15-minute intent. Stop/completion cannot be revived by replaying the same token. Leases coordinate tabs/devices and store no comments/cookies. Browser Web Locks provide an additional local duplicate guard; PostgreSQL is authoritative.

`POST /api/collection/lease` accepts `start|renew|stop|complete`, a product ID and a UUID token, reusing existing verified authentication and global origin/CSRF protections. Relay steps now require that token and renew/validate it against the authenticated owner and requested product. An old open Web bundle receives a clear 409 requesting refresh rather than performing uncoordinated network collection. Old persisted queue entries remain usable through the updated Web. Deploy Web and report worker from the same reviewed release after migration; do not mix old/new browser request contracts intentionally.

Cancel aborts the active browser relay/analyze request; the HTTP relay also aborts upstream fetch on disconnect. Ownership/account/intent checks after awaits prevent late responses from committing or enqueueing. Partial results keep list originals and warnings when detail/list reading stops. There is no proxy rotation, fingerprint change, CAPTCHA bypass or WAF evasion.

## Report progress only

The additive owner-checked job GET contract includes `displayProgress`; existing API fields remain. [ai-progress.mjs](./server/ai-progress.mjs) reads job/unit/attempt/image rows only. It does not execute inference or create jobs. Migration 011 also adds nullable `ai_units.display_phase` and `display_phase_at`; the existing report worker writes `prepare`, `model`, `persist` at real execution boundaries. Old worker rows without phase data use a conservative processing label, not a claim that the model is running. Report worker readiness now requires migration 011.

[AIProgress.tsx](./src/AIProgress.tsx) displays queued / preparation / model / persist / completion, and separate retry, fallback, recovery, partial, failed and cancelled states. The prepare counter is actual stored image-source rows with bytes / all image-source rows (not model-reviewed content or deduplicated image hashes). The model phase is indeterminate: no timer percentages, fake token counts or prepare/review 1/2=50% claim. Completion requires a valid saved readable report; partial is terminal with incomplete scope, not 100% completion. Completed reports do not animate. Legacy evidence report rendering stays unchanged.

Queue and processing wall time come from backend job/attempt timestamps; processing elapsed time includes retry waits and is labeled accordingly. A not-yet-claimed job says 等待后台处理; a long wait explains it has not been received, without claiming the worker is offline. Expired execution state says waiting for recovery. Retry/fallback text requires pending retry state and recorded fallback evidence; a real future `next_at` supplies the countdown. No ETA is invented. Poll/read errors preserve the last known state with an explicit stale-status message, rather than setting job failure. Job/account switches abort and check selection before applying responses; terminal job polling stops. Existing cancel/manual retry controls and budgets remain unchanged. DiDi's progress and queue are unaffected.
